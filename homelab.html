Section 1 · Done

Server setup

Goal: give the clinic one central server to manage logins, files and security, instead of setting up every PC on its own.

1

Built the server

What I did: I made a private virtual network called KS-ClinicNet and turned DHCP off, so I control every address. Then I built the server with 4GB RAM, 2 CPUs and a 60GB disk, and connected it to that network.

Why it matters: planning resources and networks before installing anything is how real server builds start.

2

Installed Windows Server 2025

What I did: I installed Windows Server 2025 (Desktop Experience), then the VirtualBox Guest Additions. I renamed the server to KS-DC01 and set the South African time zone.

Why it matters: a clear naming standard helps everyone find the server. The time zone matters because Active Directory logins fail when clocks don't match.

3

Gave it a fixed IP address

What I did: I set the IP to 192.168.10.10, the gateway to 192.168.10.1, and the DNS to point at the server itself (127.0.0.1).

Why it matters: a server's address must never change, or the PCs can't find it. It will also be the clinic's DNS server.

Problem I hit

The server couldn't reach the network

The trap: Windows said 4 packets were "received", but those were error messages from the server itself, not real replies.

The fix: VirtualBox won't change a network while a machine is using it, so I shut the server down, corrected the range, and started it again.

Lesson: check the device first, then the network. And always read the actual ping reply.

Section 2 · Done

Active Directory

Goal: every staff member gets their own login, sorted by department, so access is controlled from one place.

1

Installed Active Directory

What I did: I added the Active Directory Domain Services role to KS-DC01.

Why it matters: Active Directory is the tool almost every company uses to manage staff logins. It's the #1 tool on a helpdesk.

2

Created the clinic's domain

What I did: I promoted the server to a domain controller for a new domain, kasismiles.local, with DNS included.

The warning: Windows said it couldn't create a "DNS delegation". I checked what it meant: .local is a private name with no parent on the internet, so this is expected and safe.

3

Passed all checks and went live

What I did: all prerequisite checks passed, the server restarted, and the login screen now shows KASISMILES\Administrator.

Why it matters: that login name is the proof the domain exists and the server now controls it.

4

Organised the clinic into departments

What I did: I created folders called OUs: Kasi Smiles → Staff (Dentists, Clinical, Reception, Admin), plus Groups and Computers.

Why it matters: a tidy structure makes it fast to find people, and later lets me apply different rules to each department.

What I did: I ran net user /domain to list every account and net group "GRP-Reception" /domain to check the group members.

Good to know: Administrator, Guest and krbtgt are built-in accounts. krbtgt runs the domain's login "tickets" (Kerberos) and must never be deleted.

Problems I hit in Section 2

Problem 1

The server still had its default name

What I saw: just before installing Active Directory, the wizard showed WIN-24898IDELB6 instead of KS-DC01.

The fix: I cancelled, renamed the server and restarted. Renaming a domain controller later is much harder, so it had to be done first.

Problem 2

Locked out after creating the domain

What I saw: the domain existed, but my Administrator password was rejected.

What I checked: I ruled out Caps Lock and keyboard problems with the on-screen keyboard and tried every password I had used.

The fix: with no way to recover the password, I deleted the server and rebuilt it from scratch.

Problem 3

A 169.254 address after the rebuild

What I saw: the rebuilt server showed 169.254.0.81 instead of 192.168.10.10.

What it means: a 169.254 address (APIPA) is one a computer gives itself when it can't get a real one. So the static IP hadn't been set.

The fix: I set the static IP again and tested it before installing Active Directory.

Problem 4

An extra folder that wouldn't delete

What I saw: I had accidentally made a second Staff folder (bottom of the list), and it wouldn't delete.

The fix: folders are protected from accidental deletion by default. I turned on Advanced Features, removed the protection, and deleted only the extra one.

What I learned

Habits I now follow

  • Snapshot first. I save a VirtualBox snapshot before every big change, so I can undo it in seconds.
  • Test passwords straight away. I sign out and back in, then write the password down safely.
  • Check before installing. I confirm the server name and IP before adding any role.
  • Read the actual output. A number like "Received = 4" can be misleading.
